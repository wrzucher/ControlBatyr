# Ядро бизнес-логики: как проектировать

Черновик на обсуждение, 2026-11-11. Для приложения с понятной предметной областью. Примеры — игра и ставки:
это только язык примеров, саму игру документ не проектирует.

Это общий образец проектирования.

Пометки у правил: **[Р]** — решено владельцем; **[П]** — предложение лида, ждёт решения. Список предложений —
в конце.

## Термины

В тексте — русские слова, в коде — английские имена. Термины приведены к DDD, чтобы читатель, знающий DDD,
сразу понимал, что проектировать. [Р]

| У нас | В коде | В DDD |
|---|---|---|
| Менеджер | `GameManager` | Прикладная и доменная служба в одном |
| Объектная модель | `Bet` | Сущность, объект-значение |
| Бизнес-правило | `BetSpecification.CanCancel` | Спецификация |
| Код причины | `ServiceErrorCode` | — |
| Ограниченный подконтекст | `BetPersistence`, интерфейс `IBetPersistence` | Уровень над репозиторием |
| Издатель событий | `GameEventPublisher` | Издатель доменных событий |
| Событие области | `publisher.BetCancelled(…)` | Доменное событие |

**Подконтекст — это уровень над репозиторием.** Репозиторий умеет «загрузи объект — сохрани объект», и такой
уровень нам мал. Поэтому мы закрываем одной вещью всю работу с данными одного куска предметики: его методы — законченные
действия на языке бизнеса. Это не `DbContext` из EF: тот — техника внутри подконтекста.

## 1. Карта

Проектируем не слои, а **бизнес-модель области**. Она состоит из пяти вещей:

1. **объектные модели** — данные предметики;
2. **бизнес-правила** — что можно и что нельзя;
3. **менеджер** — API области: её операции;
4. **события области** — то, чем область проявляет себя наружу;
5. **связи областей** — что происходит в одной области по событию другой (раздел 9).

Хранение — способ, а не часть модели. Но способ важный: из его кубиков менеджер собирает операцию (раздел 5).

```
  Потребители: страница · API-контроллер · воркер          Другие области, внешние клиенты
        │ зовут методы менеджера                                   ▲ получают уведомления
        ▼                                                          │
 ┌──────────────────── Область «Игра» — ограниченный контекст ────────────────────┐
 │                                                                                │
 │  Объектные модели  Game · Line · Bet          данные; сами себя не меняют      │
 │  Бизнес-правила    GameSpecification · BetSpecification  чистые функции        │
 │                                                                                │
 │  GameManager       операции области; единственный, кто меняет её состояние     │
 │                                                                                │
 │  GameEventPublisher  BetPlaced · OddsChanged · BetWon · GameClosed ──────────► │
 │                                                                                │
 │  ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ кубики контекста, снаружи не видно ─ ─ ─ ─ ─ ─ ─ ─ ─      │
 │  LinePersistence · BetPersistence              под ними — DTO базы             │
 └────────────────────────────────────────────────────────────────────────────────┘
```

| Что | Работа |
|---|---|
| Объектная модель | Несёт данные предметики |
| Бизнес-правило | Отвечает, можно ли, и называет причину |
| Менеджер | Ведёт операцию: порядок шагов, изменение состояния, уведомление |
| Издатель событий | Уведомляет, что произошло в предметике |
| Подконтекст | Делает законченное действие в своём кубике контекста |

**Снаружи области видно четыре вещи:** методы менеджера, объектные модели, события области и коды причин.
Всё остальное — внутреннее дело области. [Р]

Главная мысль: **менеджер — это предметная область, записанная кодом.** Хороший метод менеджера читается как
текст: что проверяем, что делаем, о чём уведомляем.

**Зачем всё это.** Это способ создать язык предметной модели — что-то вроде DSL. Открываешь менеджер и показываешь
аналитику: «смотри, тут так». Это бизнес-слой, и читать его должен уметь не только программист. [Р]

Для этого мы управляем своим API. Объектами, правилами, методами и событиями мы описываем одну область
и её поведение — и больше ничего здесь не делаем. Поэтому всё названо предметно, и в сигнатурах нет лямбд и
обобщённых методов вроде `Publish(событие)`, `Save(объект)`, `Execute(действие)`: абстрактный метод, даже во
внутреннем API, порождает такие же абстрактные способы работы с ним. [Р]

**От простого к сложному.** Держим баланс между красотой и количеством кода. На маленьком проекте подконтексты,
интерфейсы, службы и особые проверки — оверхед. Каждая такая вещь добавляется тогда, когда без неё стало больно,
и документ говорит, как именно её добавить (раздел 9). [Р]

Сколько что живёт:

| Что | Сколько живёт |
|---|---|
| Менеджер | Единица работы: запрос, вкладка, проход воркера. **Не синглтон** [Р] |
| Подконтекст | Как его менеджер |
| Издатель событий | Синглтон [Р] |

Менеджер — корень бизнес-логики, поэтому состояния в нём нет: два вызова подряд не зависят друг от друга.

## 2. Три вида данных

| Вид | Пример | Где живёт | Кто видит |
|---|---|---|---|
| Форма хранения | сущность EF `BetEntity`, строка файла | внутри подконтекста | только подконтекст |
| Объектная модель | `Bet`, `Game` | проект ядра | менеджер, подконтекст, потребители |
| Форма потребителя | модель страницы, DTO внешнего API | у потребителя | только он |

- На вход менеджер принимает простые аргументы: идентификаторы и значения. Объектов на вход не принимает —
  API специально держим простым. Редкое исключение обсуждается отдельно. [Р]
- На выход менеджер отдаёт объектные модели и простые значения. [Р]
- Форма потребителя в ядро не попадает: ни типом, ни полем «для экрана», ни методом под один экран. [Р]
- Переводит наружная сторона: контроллер собирает свой DTO из объектной модели, страница — свою модель. В
  обратную сторону перевода нет: менеджеру уходят простые аргументы. [П]
- Потребителю нужны данные из трёх мест — он делает три вызова и собирает сам. Нового типа и метода в менеджере
  под одного потребителя не заводим. [Р]
- С этим правилом аккуратно. Если несколько вызовов идут в **один** менеджер и собранное подозрительно похоже
  на объектную модель — возможно, модели нарезаны неверно или не хватает модели, объединяющей другие. Тогда нужен
  новый метод, который возвращает новый объект. Если вызовы идут в **разные** менеджеры — объектов на пересечении
  стараемся не создавать. Каждый такой случай обсуждаем отдельно. [Р]
- Списку нужно три поля, а объект большой — пока это не проблема. Один объект на одно понятие лучше, чем
  несколько его отражений. Станет проблемой — обсуждаем. [Р]
- Объектная модель — часть внутреннего API. На раннем этапе DTO базы и объектная модель совпадают, и для
  скорости можно обойтись без отдельного типа и без подконтекста. [Р]
- Смеси не бывает: появились отдельные объектные модели — в API менеджера только они, DTO базы там больше
  нет. [Р]
- Разводим, когда они перестали совпадать. Признаки: объекту нужны методы или вычисляемые свойства, а DTO базы
  может быть сгенерирован автоматически, и держать их там негде; часть данных надо скрыть от потребителя. [Р]
- В объектной модели нет сырого: ни JSON, ни строки, которую потребитель должен разобрать. Объектная модель
  удобная и структурированная. [Р]
- Разбор JSON и других сырых данных — в подконтексте или выше менеджеров. Ядро деталями хранения не занимается:
  принимает и отдаёт только типизированное. [Р]

## 3. Менеджер

**Что это.** Менеджер — это API области. Буквально API, только внутренний, и относиться к нему надо как к API:
это не набор операций, а способ работать с областью, и другого способа нет. Исключения редкие и служебные,
например начальное наполнение данных. Самый главный слой приложения. [Р]

**Как выглядит хороший метод.** Как инструкция, написанная именами функций и переменных:

```csharp
public async Task<Bet> PlaceBetAsync(Guid gameId, Guid lineId, Guid playerId, decimal amount, CancellationToken ct)
{
    var game = await lines.GameWithLineAsync(gameId, lineId, ct);
    Require(GameSpecification.CanPlaceBet(game, lineId, amount, clock.Now));

    var bet = await bets.PlaceBetAsync(game.Id, lineId, playerId, amount, game.OddsOf(lineId), clock.Now, ct);

    publisher.BetPlaced(bet);
    return bet;
}
```

Читается это так потому, что у подконтекстов методы предметные (раздел 5), а правила названы по именам (раздел 6).
Метод, в котором видны запросы, разбор строк и циклы по полям, — признак, что чего-то из этого не хватает.

**Как выделить область.** Самое трудное место во всей схеме. Область — то, что живёт своей жизнью. Признак
чужой жизни: это мог бы вести другой сервер или другой поставщик. [Р]

- Нарезаем по жизни предметики, а не по таблицам. [Р]
- Менеджеров мало: 2–3 на приложение. Область выросла — сначала выделяем подконтексты, и только потом делим
  менеджер. Как это происходит — раздел 9. [Р]

**Простые операции тоже есть.** «Не CRUD» не значит, что в менеджере нет создания и удаления. Ставку создают и
удаляют. Но удаление ставки — операция бизнеса: проверить правило, уведомить. Имя метода — про неё. [Р]

**Доверие.** Менеджер считает, что к нему приходят нормальные данные. Контролировать всё он не может и в
какой-то степени вызывающему доверяет. Проверка формы ввода — «название обязательно», формат, длина — живёт выше
ядра, у потребителя. Сигнатура говорит сама: название в ней не допускает `null`. Подсунули кривое — метод
просто падает. [Р]

**Зависимости.** [Р]

- Свои подконтексты, издатель событий, часы. Все обязательные, через конструктор.
- Другого менеджера не зовёт. Понадобился чужой менеджер — область нарезана неверно, или это служба (раздел 9).
- Интерфейса над менеджером нет. `IServiceProvider` в менеджере нет.

**Чего в менеджере нет.** Форм потребителя; текстов для экрана. Запросов к базе — с того момента, как выделен
подконтекст (раздел 9).

## 4. Объектные модели

**Что это.** Понятия предметики: `Game`, `Line`, `Bet`. На них говорят менеджер, подконтексты и потребители.
Дальше коротко — объект.

**Снаружи объект — данные и предметные знания о себе.** Потребитель видит поля, вычисляемые свойства вроде
`bet.IsOpen` и методы, которые что-то говорят об объекте. Закрывать их не обязательно. Главное одно: данные
объект не меняет. [Р]

**Объект не управляет своим состоянием.** Без менеджера он неизменяем: состоянием области управляет только
менеджер. [Р]

```csharp
public sealed record Bet(Guid Id, Guid LineId, Guid PlayerId, decimal Amount, BetState State, DateTimeOffset GameStartsAt)
{
    public bool IsOpen => State == BetState.Open;

    public decimal RefundOnCancel(decimal fee) => Amount - fee;
}
```

Чего не делаем: `bet.Cancel()` меняет поля внутри объекта, а менеджеру потом надо догадаться, что и каким методом
сохранить.

**Где логика: в менеджере, в объекте или в правилах.** Бывает по-разному: толстый менеджер и тонкие объекты,
или наоборот. Жёсткого правила нет, решает место. Это внутреннее дело области: что мы убрали из менеджера, чтобы
он не толстел, снаружи не видно. Ориентир один — менеджер читается как текст. [Р]

## 5. Ограниченный подконтекст

**Что это.** Кубик ограниченного контекста. Сложный бизнес-процесс всегда состоит из нескольких контекстов
поменьше. Ограниченный подконтекст — один такой контекст вместе с его хранением; дальше коротко — подконтекст.
Это не `DbContext` из EF, не путать: `DbContext` — техника внутри подконтекста. Менеджер собирает операцию из кубиков. [Р]

**Методы предметные, как у менеджера.** Не «прочитай строку» и «сохрани строку», а законченное действие на языке
бизнеса. Метод подконтекста может быть таким же сложным, как метод менеджера. Именно поэтому менеджер читается
как текст. [Р]

```csharp
public interface IBetPersistence
{
    Task<Bet?> BetAsync(Guid betId, CancellationToken ct);
    Task<IReadOnlyList<Bet>> OpenBetsOfGameAsync(Guid gameId, CancellationToken ct);
    Task<Bet> PlaceBetAsync(Guid gameId, Guid lineId, Guid playerId, decimal amount, decimal odds, DateTimeOffset at, CancellationToken ct);
    Task CancelBetAsync(Guid betId, DateTimeOffset at, CancellationToken ct);
    Task<IReadOnlyList<Bet>> SettleBetsOfLineAsync(Guid lineId, LineOutcome outcome, DateTimeOffset at, CancellationToken ct);
}
```

| Репозиторий — не так | Подконтекст — так |
|---|---|
| `GetById`, `Save(bet)`, `Update(bet)` | `PlaceBetAsync(…)`, `SettleBetsOfLineAsync(…)` |
| Менеджер читает, правит поля, сохраняет | Менеджер называет действие, кубик делает его целиком |

- Метод говорит, что именно он запишет, и принимает то, что для этого нужно. `Save(bet)` — плохо: отдали объект
  целиком, и непонятно, что с ним сделают. [Р]
- Чем кубик отличается от менеджера: он не решает, можно ли (правила применяет менеджер), и не уведомляет. [Р]
- **Подконтекст — API предметики, а не API хранения.** Он закрывает работу с куском предметной области, который
  лежит в базе или где-то ещё, например в git-репозитории и файлах. Наружу у него нет ни таблиц, ни файлов —
  только предметные действия. [Р]
- Расчёт может жить и в подконтексте: большая хранимая процедура, сложный запрос. Проблемы в этом нет. [Р]
- Образ: менеджер — департамент, подконтексты — отделы внутри него. У отдела свои задачи, и он их просто
  выполняет. [Р]
- Внутри подконтекста — формы хранения (DTO базы). Наружу — только объектные модели. [Р]
- **У подконтекста ровно один менеджер. У менеджера их может быть несколько.** Два менеджера один подконтекст
  не зовут — без исключений. [Р]
- **Целостность — внутри одного метода подконтекста:** либо упало, либо записано целиком; это даёт EF или
  другое хранилище. Поэтому метод крупный. [Р]
- **Метод менеджера транзакцией не оборачиваем.** Упадёт однажды на полпути — редкий случай. Появится проблема
  — решим её точечно. Заранее транзакции в архитектуру не закладываем: для небольшого проекта это оверхед. [Р]
- В коде — `…Persistence`, без `Db`: `BetPersistence`, интерфейс `IBetPersistence`. Имя одно, даже если внутри
  файлы. [Р]
- Интерфейс над подконтекстом — нормально: с ним бизнес-часть тестируется на тестовом подконтексте. Но не сразу и
  не везде: вводим, когда область усложнилась и её хочется проверять отдельно (раздел 9). [Р]
- В маленьком проекте подконтекст — оверхед: можно не вводить (раздел 9). [Р]

## 6. Бизнес-правила

Бизнес-валидация и бизнес-правило — одно и то же (проверки формы — отдельный вид, ниже). Правило пишется один раз и применяется двумя способами: спросить
заранее и потребовать перед записью. [Р]

**Проверка — метод менеджера.** Бизнес-проверка почти всегда начинается с чтения: посмотреть, что в базе, и
решить. Поэтому единица проверки — метод менеджера. Он читает что нужно и возвращает список кодов причин; пустой
список — можно. [Р]

```csharp
// проверка: читает и решает
public async Task<IReadOnlyList<ServiceErrorCode>> CancelBetProblemAsync(Guid betId, CancellationToken ct)
{
    var bet = await bets.BetAsync(betId, ct);
    if (bet is null) { return [ServiceErrorCode.BetNotFound]; }

    return BetSpecification.CanCancel(bet, clock.Now);
}

// действие: требует ту же проверку
public async Task CancelBetAsync(Guid betId, CancellationToken ct)
{
    Require(await CancelBetProblemAsync(betId, ct));     // бросает исключение с теми же кодами

    await bets.CancelBetAsync(betId, clock.Now, ct);

    publisher.BetCancelled(betId);
}
```

**Чистая функция — приём, а не закон.** Когда в решении есть что выносить — несколько условий, расчёт, — оно
уходит в спецификацию: чистую функцию, которой менеджер передаёт уже прочитанное. Проверка из одного вопроса к
базе живёт прямо в методе менеджера. [Р]

```csharp
internal static class BetSpecification
{
    public static IReadOnlyList<ServiceErrorCode> CanCancel(Bet bet, DateTimeOffset now)
    {
        var problems = new List<ServiceErrorCode>();
        if (bet.State != BetState.Open) { problems.Add(ServiceErrorCode.BetAlreadySettled); }
        if (now > bet.GameStartsAt) { problems.Add(ServiceErrorCode.GameStarted); }
        return problems;
    }
}
```

- Объекта нет: действие просто падает. Причину заранее отдаёт проверка — если она нужна, для неё есть метод.
  Действие, которое ничего не возвращает, может вернуть код вместо `void`. Зависит от метода; заранее всё не
  размериваем. [Р]
- Вопросы к данным задаёт подконтекст, предметными методами. Без фанатизма: есть `OpenBetOnLineAsync` — отдельный
  `HasOpenBetOnLineAsync` ради проверки не заводим. API подконтекста не раздуваем. [Р]
- **Между проверкой и записью данные могут измениться.** Последний рубеж — подконтекст: он упадёт на ограничении
  базы. Это мелочь; станет частым — решим по месту. [Р]
- Спецификации закрыты (`internal`). Потребитель правило не вызывает и не повторяет: спрашивает менеджер. [Р]
- **Проверка полная.** Стараемся записать в неё все правила, в том числе те, что продублированы ограничениями
  в базе: иначе человек получит общую ошибку вместо причины. Дублировать ради этого — нормально. [Р]
- Отдельно написанной бизнес-валидации нет. Двух проверок одного значения с разными правилами не бывает. [Р]
- Причин может быть несколько, и наружу выходят все, а не первая. [Р]
- **`…Problem` делаем публичным только там, где его кто-то спрашивает:** есть кнопка или ответ API, которому
  причина нужна заранее. Иначе проверка остаётся внутри действия. [Р]
- **По месту, не везде:** когда у объекта несколько действий, вместо `…Problem` на каждое можно дать один метод
  «что сейчас можно сделать с объектом» — `BetActionsAsync(betId)` с причинами по каждому действию. [Р]
- Одно действие — два метода: это по-прежнему беспокоит (раздел 13).

**Виды проверок.** Проверки бывают разные, и живут они в разных местах: [Р]

| Вид | Пример | Где |
|---|---|---|
| Формат ввода | число, дата, длина строки | на форме, у потребителя |
| Связность формы | поле обязательно; при таком значении одного поля у другого допустимы только такие | на форме, у потребителя |
| Бизнес-правило | ставку нельзя отменить после начала игры | менеджер: `…Problem` и `Require` |

- **Граница:** чтобы ответить, надо прочитать данные области — это бизнес-правило; хватает самой формы — это
  форма. «При типе А допустимы значения 1–3» — форма. «Допустимы только линии, открытые в этой игре» —
  менеджер. [Р]
- Менеджер — это уже бизнес-ввод: входные проверки закончены, осталось принять или упасть (раздел 3). [Р]
- Обычно форма живёт в админке или клиентском приложении и зовёт API сервера, а не менеджер. Страница
  Blazor, которая зовёт менеджер напрямую, — наше упрощение. Сырой ввод от второго потребителя — редкий случай:
  появится — обсудим. [Р]
- Не решено: бывает ли проверка в объекте (раздел 13).

**Отказ.**

- Бизнес-метод не боится падать: `Require` бросает исключение отказа с кодами. Нестандартный ход может упасть. [Р]
- Исключение отказа одно, в нём коды. Потребитель берёт коды и показывает или отдаёт их; текст
  исключения не разбирает и по видам исключений не ветвится. [П]

**Код причины.** Проверка возвращает не текст, а код. Текста в ядре нет: как показать код человеку и перевести
на языки — дело фронта. [Р]

- Начинаем с одного enum на всё приложение — `ServiceErrorCode`. Значения сгруппированы по десяткам. Вырастет
  и станет много — делим на подкоды. [Р]
- Код не несёт данных. «На шаг ссылаются, удалить нельзя» — это код и всё. Что именно ссылается, человеку
  должно быть удобно увидеть на экране другим способом. [Р]
- Кодом покрывается не всё. Понадобится что-то особое — заводим особую проверку, по месту. Начинаем с простого
  и усложняем, когда стало нужно. [Р]
- На границе внешнего API ответ обычно один на всё: результат операции с кодом. Это форма контроллера. [Р]
- Внутри ядра полного `Result<T>` во всех методах нет: `…Problem` отдаёт коды, остальное — исключения. [Р]

## 7. Потребители

Страница и контроллер устроены одинаково: принять ввод → проверить форму → позвать менеджер простыми
аргументами → перевести ответ или отказ.

```csharp
[HttpPost("games/{gameId}/bets")]
public async Task<ActionResult<BetResponse>> Place(Guid gameId, PlaceBetRequest request, CancellationToken ct)
{
    var bet = await games.PlaceBetAsync(gameId, request.LineId, CurrentPlayerId, request.Amount, ct);   // отказ → 4xx фильтром
    return BetResponse.From(bet);                                                      // свой DTO, не Bet
}
```

- У внешнего API свои DTO, они лежат в его проекте. Объектная модель наружу не отдаётся: иначе внешний контракт
  меняется при каждой правке ядра. [Р]
- Правил предметики у потребителя нет. Условие «можно ли» он спрашивает у менеджера. [Р]
- Экранное состояние — выбор, фильтры, раскрытое, черновик ввода — живёт в компоненте. Его записи и классы лежат
  в том же `.razor` или рядом. [Р]
- Потребитель не знает устройства хранения: не склеивает адреса, не приводит идентификаторы, не знает имён
  файлов. [Р]

## 8. События области

События — такая же часть бизнес-модели, как объекты и операции менеджера. Это проявление области наружу.
Проектируются так же аккуратно, как методы менеджера. [Р]

- Событие — факт предметики на её языке: «ставка сыграла», «на линии новый коэффициент». Не «что-то изменилось»
  и не «строка обновлена». [Р]
- Событие принадлежит области. «Ставка сыграла» — событие игры; что делать по нему дальше — дело того, кто
  слушает. [Р]
- Поднимает событие менеджер: последней строкой метода, после записи. [Р]
- **Событие может потеряться:** запись прошла, процесс упал, уведомления не было. Знаем и заранее не закрываем:
  решать будем по месту, когда это станет настоящей проблемой. Сейчас удобство и скорость развития важнее. [Р]
- **Менеджер о механизме не знает.** У него есть издатель событий — класс-прослойка «уведомить, что случилось
  вот это»: `publisher.BetCancelled(bet.Id)` — «уведомить, что ставка отменена». Как уведомление дойдёт —
  событием, хабом SignalR, ещё как-то — это техника, а не бизнес-логика. [Р]
- Метод на каждое событие. Общего `Publish(событие)` нет: абстрактный метод порождает абстрактную работу с ним,
  а своим API мы управляем (раздел 1). [Р]
- Издатель событий — синглтон, по одному на область: `GameEventPublisher`. [Р]
- Слушают: другая область, внешний клиент через SignalR, страница. [Р]
- Названия держим строго: одно происшествие — одно имя и в издателе событий, и в событии, и в контракте SignalR. [Р]
- Страница в обработчике данные не меняет: просит свежие данные у менеджера и перерисовывается. [П]

Внутри издателя — обычный `event`, подписка — раздел 9. Понадобится хаб или брокер — он встанет за издателем,
менеджер этого не заметит. Не решено одно: где записан контракт событий для внешних клиентов.

## 9. Как область растёт и делится

Сначала в один менеджер можно сложить всё. С ростом продукта он усложняется и дробится. Правила нужны, чтобы
знать, когда и что выделять, а не мучиться потом. [Р]

| Шаг | Признак, что пора |
|---|---|
| Менеджер сам работает с базой (`DbContext` внутри) | Начало: проект маленький, подконтекст был бы оверхедом [Р] |
| Появляются объектные модели; подконтекстов ещё нет | DTO базы перестали совпадать с тем, что нужно API менеджера (раздел 2) [Р] |
| Выделяем подконтексты, зависимости уходят ниже | Менеджер усложнился: в методах видны запросы, метод перестал читаться как текст [Р] |
| Интерфейсы над подконтекстами | Область сложная, хотим тестировать бизнес-часть отдельно от базы [Р] |
| Менеджер делится | Часть зажила своей жизнью: свои события, свои потребители [П] |

После деления области связаны двумя способами. Оба — бизнес-знание, а не техника.

**Цепочка у потребителя.** Позвать несколько менеджеров подряд — нормально: в контроллере, на странице,
в интеграции. В том числе с записью. Особенно пока проект маленький. [Р]

```csharp
await accounts.BlockAsync(playerId, amount, ct);                    // проверить деньги и заблокировать
try
{
    var bet = await games.PlaceBetAsync(gameId, lineId, playerId, amount, ct);
    await accounts.ChargeBlockedAsync(playerId, bet.Id, ct);        // списать заблокированное по ставке
}
catch
{
    await accounts.UnblockAsync(playerId, amount, ct);
    throw;
}
```

- Это похоже на сагу, но отдельный слой под неё заранее не проектируем. [Р]
- Менеджер менеджера не зовёт. [Р]

**Связь по событию.** В одной области что-то произошло — в другой что-то делается. [Р]

- Это дешёвая подписка: у издателя событий внутри обычный `event`, на него подписывают действие другой области —
  взять из скоупа её менеджер и позвать метод. Проще некуда. [Р]
- **Связи — самое важное бизнес-знание.** «Ставка сыграла → зачислить выигрыш» — такая же часть модели, как
  метод менеджера. Держим их так же строго: в ядре, на виду, с предметными именами. [Р]
- Понадобится доставлять надёжнее — меняем доставку. Связи и менеджеры при этом не меняются. [Р]

Набросок, как это может выглядеть. Техника здесь не решена: [П]

```csharp
internal sealed class GameAccountLinks(GameEventPublisher games, IServiceScopeFactory scopes)
{
    public void Connect() => games.BetWon += CreditWinAsync;        // ставка сыграла → зачислить выигрыш

    private async Task CreditWinAsync(Guid betId, Guid playerId, decimal payout)
    {
        await using var scope = scopes.CreateAsyncScope();
        var accounts = scope.ServiceProvider.GetRequiredService<AccountManager>();
        await accounts.CreditWinAsync(playerId, betId, payout, CancellationToken.None);
    }
}
```

Связи лежат в ядре (раздел 16). Нужен ли им свой тип — не решено. Мысли владельца: связи могут быть прообразом службы —
служба и отвечает за взаимодействие областей; а может быть, отдельный тип не нужен, и связи создаёт сам издатель
событий.

**Служба.** Цепочка повторяется и несёт свой смысл — это служба: взаимодействие департаментов. [Р]

- Служба зависит только от менеджеров, в базу не ходит, ничем не владеет. [Р]
- На маленьком проекте служба — оверхед: это уже уровень саги, и мы оттягиваем его, сколько можем. Добавить её,
  когда понадобится, — не проблема. [Р]
- Перед тем как делать службу, проверяем, верно ли нарезаны менеджеры: возможно, контексты разделены не там. [Р]
- Признак ошибки слоя: у типа нет своего подконтекста и ему нужны менеджеры — это служба, названная
  менеджером. [Р]

Общее для всех трёх: как связаны события и как откатывать цепочку — технические вопросы, решаются по месту.
Главное — бизнес-слой: что из ядра видно снаружи. [Р]

Подконтекст при делении менеджера уходит к одному из менеджеров целиком: хозяин у него один. [Р]

## 10. Исключения из правил

Это правила проектирования, а не закон природы. В настоящем проекте будут места, куда они не ложатся.

- Исключение не делается молча. Лид приносит его владельцу: какое правило, почему не подходит, что взамен.
- Решение записывается в реестр отступлений: место в коде, правило, почему, как сделано.
- Три похожих исключения — повод обсудить само правило.

Известный трудный случай — **workflow**: состояние — факты, меняют его шаги, топология живёт в определениях.
Где в этой картине менеджер и кто хозяин изменения — неочевидно. Разбирается отдельным документом.

## 11. Как это соотносится с DDD

Это DDD по сути, с двумя сознательными отступлениями.

| DDD | У нас |
|---|---|
| Ограниченный контекст | Область менеджера |
| Репозиторий | Подконтекст — уровень над ним |
| Сущности и объекты-значения | Объектные модели |
| Спецификация | Бизнес-правило |
| Прикладная и доменная служба | Менеджер — обе в одном |
| Издатель доменных событий | Издатель событий |
| Доменное событие | Событие области |
| Слой защиты от чужой модели | Шлюз к удалённому серверу |

Отступления:

- **Нет агрегата, который сам меняет себя и сохраняется целиком.** У нас объект неизменяем, меняет менеджер.
  Хозяин правила при этом один — менеджер области: он применяет проверку перед каждой записью.
- **Нет репозитория «загрузи объект — сохрани объект».** У нас метод подконтекста называет, что именно он пишет.

**Можно ли потом разнести по службам с брокером сообщений.** Да, и правила этому не мешают, а готовят:

- менеджер не зовёт менеджер — между областями уже нет прямых вызовов;
- у подконтекста один хозяин — данные области можно унести в свою базу;
- две области одной операцией не пишут;
- события — факты предметики; за издателем событий встаёт публикация в брокер; менеджер этого не замечает.

Что придётся доделать при разносе: событие должно нести все данные, нужные подписчику (сейчас он может
переспросить менеджер); потребитель, который звал два менеджера подряд, станет клиентом двух служб.

## 12. Как не надо

| Что сделали | Почему плохо |
| --- | --- |
| Статический помощник принимает базу и стоит рядом с менеджерами | Данные области читают в обход её хозяина |
| Тип и метод в менеджере под один экран | Фронт прорастает в ядро, менеджер пухнет |
| Новый тип ради одного вызова | То же отдают два существующих метода |
| Экранные модели в ядре | Ядро знает про выбор и фильтры страницы |
| Контроллер сам пишет данные | У изменения нет хозяина и причины |
| Интерфейс над менеджером ради теста | Код существует не ради продукта |
| Необязательная зависимость в конструкторе | Молча выключает обязательный эффект |
| Менеджер зовёт менеджер | Область нарезана неверно |
| Правило написано дважды: на странице и в менеджере | Разойдутся; клиент и сервер отвечают по-разному |
| Событие «что-то изменилось» | Подписчик не знает, что произошло в предметике |
| `Save(объект)` в подконтексте | Непонятно, что метод запишет |
| Объект меняет свои поля сам | Менеджер должен догадаться, что сохранить |
| Метод менеджера из запросов и циклов | Не читается как текст: не хватает методов подконтекста или правил |

## 13. Не решено

Сюда не пишем, как будет, пока владелец не решит. Нужно в коде — сначала вопрос владельцу.

- **Данные в памяти и кэш.** Сейчас задач для кэша в менеджере нет. Как держать горячие данные — не решено;
  скорее отдельное хранилище в памяти, чем подконтекст.
- **Тесты и BDD** (раздел 15).
- **Клиент и сервер:** как клиент узнаёт, что можно, не повторяя правил (раздел 6).
- **Контракт событий для внешних клиентов** (раздел 8) и техника связи по событию (раздел 9).
- **Удалённый сервер.** Типизированное API за шлюзом. Работает ли с ним менеджер — не решено.
- **Виды проверок:** бывает ли проверка в объекте (раздел 6).
- **Одно действие — два метода** (действие и `…Problem`): терпим, лучшего способа пока нет (раздел 6).
- **Документация из ядра** и требования к комментариям (раздел 17).
- **Удобный способ писать и проверять спецификации:** чтобы их можно было читать как требования (BDD) или
  собирать из требований.
- **Долгая работа, команды и воркеры; workflow** — отдельные документы.

## 14. О чём спрашивать владельца

- новый менеджер, подконтекст или служба;
- менеджеру нужны данные чужого подконтекста;
- новый публичный метод менеджера, новое событие, новый внешний API;
- что-то хочется запомнить в памяти;
- правило из этого документа мешает сделать задачу.

Остальное внутри карты решает лид.

## 15. Тесты — обсудим отдельно

Правила проектирования тестов — важная тема и отдельное обсуждение. Позиции владельца, от которых оно пойдёт: [Р]

- **Каждый тест — проверка бизнес-требования. Иначе он не нужен, это мусор.** Неважно, BDD это или юнит-тест,
  на менеджер, на контроллер или на страницу: тест читается как требование бизнеса.
- **Тест читается как текст — теми же словами, что менеджер.** Тест и менеджер — инь и ян: одно требование,
  записанное с двух сторон.
- **Форма теста:** название требования; условие, при котором оно применяется (Arrange); действие (Act); проверка,
  что требование выполнено (Assert).
- **В теле теста — только требование.** Подготовка данных, сборка объектов и прочая техника уходят в помощники
  и статические методы. В BDD то же самое: шаги написаны словами бизнеса.
- **Тест на каждый метод не нужен и вреден.** Проверки помощников «при таком входе вот это» — тот самый мусор.
  Важно бизнес-API: методы менеджера, правила, события.
- **Интересно тестирование от менеджера до подконтекста.** Можно и на тестовом подконтексте — для этого
  интерфейс над ним (раздел 5).
- **Менеджер — родное место для BDD.** Сценарии (Gherkin) обычно и пишутся на этот слой. Копать пока не будем.

Сейчас тесты пишутся на всё и захламляются — это то, от чего уходим.

Тест бизнес-слоя попадает в документ ядра (раздел 17), поэтому у него есть форма: [Р]

- **В теле теста менеджер зовётся один раз** — это и есть действие. Появился второй вызов — сборка говорит:
  убери или пометь тест явно, какое действие он проверяет. Лучше убрать.
- Тестировать можно что угодно. Но тест не про бизнес-слой живёт отдельно и в документ не попадает.

Не решено: насколько жёстко навязывать форму теста. Обязательные помощники вроде `Given.…` пугают: есть шанс,
что тесты от них лучше не станут.

## 16. Структура проектов

Цель: проект ядра, где минимум техники и максимум бизнес-знания, и где всегда известно, что в нём публичное. [Р]

Проекты появляются по мере роста (раздел 9): [Р]

| Этап | Проекты |
|---|---|
| Начало | `Core` и проект EF с `DbContext` и DTO базы. Менеджер работает с DTO напрямую |
| Появились объектные модели | Те же два проекта. Объектные модели лежат в `Core` |
| Выделены подконтексты | `Core` → `Persistence` → проект EF; объектные модели уходят в `Model` — ниже |

Потребители (`Api`, `Web`) и тесты — отдельные проекты на любом этапе.

**Где лежат подконтексты.** Требования: [Р]

- подконтекст возвращает объектные модели;
- подконтексты лежат не в одном проекте с менеджерами;
- объектные модели могут спокойно расти;
- пока подконтекстов и объектных моделей нет, можно работать с DTO базы;
- ядро зависит от проекта EF, и это нормально: абстрагировать это глупо, ядру всё равно ходить в базу.

Поэтому объектные модели уходят в отдельный проект. Имя — `Model` или `ObjectModels`, выбирает лид: [Р]

```
Core (менеджеры, спецификации, издатели, связи) → Persistence (подконтексты) → EF (DbContext, DTO базы)
        └────────────────────────────┴──────────→ Model (объектные модели, коды причин)
```

- Цикла нет, цепочка прямая. Проект `Model` появляется вместе с подконтекстами, не раньше.
- Закрыть логику объекта при этом нельзя: из другого проекта ядру она не видна. Это принято: предметные
  методы объекта публичные (раздел 4). [Р]
- Потребитель через ссылку на ядро видит и подконтексты. Это не страшно, без фанатизма. [Р]

Что в ядре публичное — ровно то, что видно снаружи области (раздел 1): [П]

- менеджеры и их методы;
- объектные модели: данные, вычисляемые свойства и предметные методы;
- коды причин и исключение отказа;
- события издателей — сторона подписки.

Закрыто: спецификации и сторона издателя «уведомить». Подконтексты закрывать не обязательно.

- Связи областей лежат в ядре, в одном месте, и читаются списком «событие → действие». Техника подписки —
  создать скоуп, взять менеджер, позвать метод — пока тоже в ядре: её немного. [Р]
- Публичное API тестом-описью не охраняем: это уже слишком. [Р]

## 17. Комментарии и документация ядра

Требования к документированию — отдельная тема, как и тесты. Позиции владельца: [Р]

- **Комментарий — бизнес-комментарий.** Он говорит то, чего нет в коде: зачем правило, что оно значит для
  предметики, откуда требование.
- **Комментарий не пересказывает код.** Описание кода словами — слоп и трата токенов. У комментария должна быть
  ценность, иначе его не пишем.
- **Зачем это всё: документ из ядра — готовый контекст для агента.** Не надо ходить по коду: вот API, вот
  объекты, вот события, вот связи, вот требования. Чем больше менеджеров, тем это ценнее.

**Фреймворк.** Одни и те же правила обсуждаются в каждом продукте, и в каждом код в итоге скатывается.
Поэтому подход должен стать фреймворком, который заставляет агентов принимать решения по этим правилам. [Р]

- Из исходников ядра и тестов собирается документ, как OpenAPI: методы менеджеров, отказы, события, связи,
  требования из тестов.
- Нарушено правило или документ собрать нельзя — сборка падает; на худой конец предупреждает.
- Порядок: сначала заканчиваем этот документ. Потом пробуем на настоящем продукте.
- Главный риск — кривой фреймворк на костылях. Поэтому каждое правило проектируем сразу с вопросом, как его
  проверит сборка.

Набросок, владельцу нравится, не решено: связь записывается методом с пометкой события —
`[On<GameEventPublisher>(nameof(GameEventPublisher.BetWon))]`, подписку дописывает генератор. Как тест
привязывается к методу менеджера — раздел 15.
