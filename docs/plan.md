# План ControlBatyr

Состояние: 2026-11-12, до первого шага. Решения владельца помечены [Р], предложения лида — [П].

## Зачем

Ядро бизнес-логики проектируется по одному образцу: менеджер — API области, объектные модели, бизнес-правила,
события, связи областей. В каждом продукте правила обсуждаются заново, и код всё равно скатывается. Библиотека
должна удерживать форму сама — и для людей, и для ИИ-агентов. [Р]

1. **Документ из ядра** — цель номер один. Как OpenAPI из контроллеров: методы менеджеров, объекты, события,
   связи, требования из тестов. [Р]
2. **Падение, когда правило нарушено** или документ собрать нельзя. [Р]
3. **Примитивы из коробки**, с которыми писать по образцу проще, чем мимо него. [Р]

## Откуда библиотека берёт знания

Три вида знаний — три способа. Разбора исходников (Roslyn) в первой версии нет. [П]

| Знание | Пример | Способ |
|---|---|---|
| Форма | менеджеры, методы, аргументы, объекты, события издателя, коды | отражение собранной сборки и файл xmldoc |
| Утверждение человека | «этот тест — требование к этому методу», «по этому событию — это действие» | атрибут: `[Requirement]`, `[On]` |
| Поведение в теле метода | какое событие поднимает метод, какими кодами отказывает | в первой версии не берём; шаг 4 |

Роли типов узнаются по именам из образца: `…Manager`, `…Persistence`, `…EventPublisher`, `…Specification`.
Атрибут — только там, где по форме узнать нельзя.

## Состав репозитория

```
Directory.Build.props         .NET 10, Nullable, предупреждения — ошибки
src/ControlBatyr              на него ссылается ядро продукта: отказ с кодами и Require, [On]
src/ControlBatyr.Inspection   на него ссылаются тесты: чтение ядра, правила, сборка документа, [Requirement]
tests/ControlBatyr.Tests      тесты библиотеки: маленькие «кривые ядра», на которых правило обязано упасть
sample/Game.Model             объектная модель и коды причин
sample/Game.Persistence       подконтекст на SQLite в памяти
sample/Game.Core              один менеджер, спецификация, издатель событий
sample/Game.Tests             тесты-требования и тест «документ собран и не устарел»
sample/docs/core.md           собранный документ; лежит в репозитории, чтобы его читать
.github/workflows/ci.yml      сборка и тесты
```

Пример — выдуманная игра со ставками: одна область, 2–3 метода менеджера. Это язык примера, саму игру не
проектируем.

## Шаги

Каждый шаг — отдельный pull request. После каждого — показ владельцу и решение, идём ли дальше.

| № | Что делаем | Готово, когда |
|---|---|---|
| 1 | Пример по образцу и минимум примитивов: отказ с кодами, `Require` | Сборка и тесты зелёные; метод менеджера читается как текст; каждый тест — требование |
| 2 | Документ: отражение, xmldoc, `[Requirement]` | `sample/docs/core.md` собирается тестом; CI падает, если он устарел; владелец прочитал и сказал, годится ли вид |
| 3 | Правила по форме (ниже) | На примере нарушений нет; на каждое правило есть «кривое ядро», где оно падает с понятным сообщением |
| 4 | Опыт: поведение в теле метода двумя способами (ниже) | Владелец выбрал способ или отказался от этой части |
| 5 | Вторая область и связи `[On]`; связи в документе | Связь работает в тесте и видна в документе строкой «событие → действие» |
| 6 | Решения по итогам: анализатор сборки, пакет NuGet, проба на настоящем продукте | — |

**Правила шага 3**, все проверяются отражением:

- менеджер не получает в конструкторе другой менеджер и `IServiceProvider`;
- методы менеджера принимают только простые значения, объектных моделей на входе нет;
- у подконтекста ровно один менеджер;
- у издателя нет обобщённого метода и метода, принимающего «любое событие»;
- у публичного метода менеджера и у события есть комментарий — иначе документ не собрать;
- объектная модель не меняет своих данных: изменяемых свойств нет.

Метод без требований сборку не роняет: в документе у него стоит «требований нет».

**Опыт шага 4.** Два способа узнать, что метод поднимает и чем отказывает:

- *Наблюдение.* Издатель и `Require` во время тестов записывают, что произошло; в документ идёт увиденное.
  Чего тесты не покрыли, того в документе нет, и это видно.
- *Разбор кода.* Roslyn читает тело метода. Надёжно только там, где форма жёсткая: издатель зовётся прямо в
  методе менеджера.

Пробуем оба на примере и сравниваем по количеству кода и по числу мест, где способ ошибся.

## Критика

- **Падение на тестах, а не на сборке.** Отражению нужна собранная сборка, поэтому нарушение видно на
  `dotnet test`. Для агента это тот же цикл, но в редакторе ошибки нет. Правила шага 3 позже можно перенести
  в анализатор Roslyn без изменений смысла — это решение шага 6.
- **Библиотека проверяет форму, а не смысл.** Метод `Process(Guid id)` пройдёт все правила. Качество имён
  остаётся на ревью.
- **Игрушечный пример всё прощает.** Трудные места образца — долгая работа, воркеры, данные в памяти — в него
  не попадают. Настоящая проверка — проба на продукте, шаг 6.
- **xmldoc и «предупреждения — ошибки».** Включённый файл документации требует комментарий к каждому публичному
  члену — это прямой путь к пересказу кода. Это предупреждение выключаем; комментарий требует наше правило и
  только там, где он идёт в документ.
- **Атрибуты `[Requirement]` и `[On]` повторяют то, что видно в коде глазами.** Это осознанная цена: взамен нет
  угадывания.
- **Риск костыльного фреймворка.** Защита одна: примитив добавляется, только если убирает код из примера.

## Не решено

- Где живёт документ-образец: копия здесь или ссылка. Он лежит в закрытом репозитории и упоминает закрытый код.
- Имена пакетов и публичное API библиотеки — показываются владельцу на шаге 1.
- Насколько жёстко навязывать форму теста.
- Свой тип для связей или служба — до шага 5.
