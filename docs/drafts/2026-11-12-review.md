# Ревизия ControlBatyr и идеи владельца — черновик

2026-11-12. Черновик на русском по разрешению владельца; перед публичным выпуском почистить.
Здесь три вещи: что построено, идеи владельца в структурированном виде, анализ лида.

## 1. Что построено за день

| Часть | Пакет | Состояние |
|---|---|---|
| Атрибуты ролей: менеджер, объектная модель, издатель событий, подконтекст | `ControlBatyr` | готово |
| Связи областей `[On<T>]` и их подключение при старте (`ConnectDomains`) | `ControlBatyr` | готово; это рабочий код продукта, а не документация |
| Документ бизнес-API при сборке: операции, события, модели, связи, файл на область | `ControlBatyr.Inspection` | готово |
| Требования из тестов `[Requirement<T>]` | `ControlBatyr.Requirements` | готово |
| Правила формы CB0001–CB0007 | `ControlBatyr.Rules` | готово, по желанию |
| Пакеты и проверка их установки | — | собраны, не опубликованы |

Принципы, которые держим: роль задаёт атрибут, а не имя; внутрь методов не лезем; первая версия — только
документация; проверка — расширение.

## 2. Идеи владельца (2026-11-12)

1. **ИИ — отдельное расширение.** Не агенты, а простые вызовы внешнего провайдера. Интерфейс — `IChatClient`
   из `Microsoft.Extensions.AI`; какой провайдер — дело потребителя.
2. **Не на каждую сборку.** Перегенерировать, когда изменился код; модель дешёвая.
3. **Обход и события.** Обход кода порождает события (что-то вроде посетителя); «обзор области», «требования
   человеческим языком», обобщение знаний строятся на этих событиях — нами или кем-то ещё. Хочет кто-то
   ИИ-слоп — пусть добавляет сам, библиотека даёт только возможность.
4. **Промтов в библиотеке быть не должно.** Допустимы промты по умолчанию, но любой можно переопределить.
5. **Сценарии Reqnroll и документация** должны быть связаны, возможно через ИИ-помощника.
6. **Диаграммы Mermaid** классов; желательно по спецификации архитектурных диаграмм из SayBatyr
   (`classDiagram` + директивы `%% @arch/1`).
7. **Ручной Markdown вместе с собранным.** Картина не ясна. Смысл — целостность: документы вшиты в
   документацию как источники данных или ссылки.
8. **Больше мяса в бизнес-слое.** Больше текста: use cases, сценарии — но с основаниями, которые можно
   проверить. Не один вызов модели, а несколько, с супервизией — как в концепции workflow и фактов SayBatyr.

## 3. Анализ

### 3.1 Главное: мы пропустили модель

OpenAPI силён не страницей Swagger, а файлом спецификации: один раз прочитали код → получили типизированное
описание → дальше с ним работает кто угодно. Мы сразу пишем Markdown: чтение сборки и вывод текста сейчас
слиты в одном классе на 450 строк.

Все восемь идей владельца упираются в одно и то же — нужна **модель бизнес-API** между кодом и документом:

```
сборки ──чтение──► модель бизнес-API ──► Markdown
                   (области, операции,   ──► диаграмма Mermaid
                    события, модели,     ──► правила
                    связи, требования)   ──► ИИ-обогащение
                         ▲
        Reqnroll, ручные документы — добавляют свои узлы и ссылки
```

«Обход, который порождает события» — это и есть желание иметь модель и точки расширения. Сама модель проще
потока событий: обзору области нужна вся область сразу, а не событие за событием. Посетитель по модели
даётся бесплатно.

Следующий шаг поэтому не новая возможность, а перестройка: чтение отдельно, модель отдельно (и файлом рядом
с документами), вывод отдельно. Поведение не меняется.

### 3.2 Один идентификатор на всё

У узла модели нужен устойчивый идентификатор. Он уже существует: идентификаторы xmldoc
(`T:Game.Core.GameManager`, `M:…CancelBetAsync(System.Guid,…)`), и спецификация диаграмм SayBatyr использует
ровно их с префиксом сборки.

Один идентификатор связывает всё: якорь в документе, директиву `@arch` в диаграмме, ссылку требования, тег
сценария Reqnroll, вставку в ручной документ и основание ИИ-утверждения. Это и есть «целостность».

### 3.3 ИИ: основания выбором, а не текстом

Принцип из SayBatyr («ссылка выбором»): модели дают пронумерованный вход и разрешают в ответе только эти
номера. Сослаться на непредъявленное невозможно, а проверяет это обычный код.

Для нас: каждое сгенерированное утверждение («игрок может отменить ставку до начала игры») несёт
идентификаторы узлов, на которых основано: операция, требование, событие. Тогда:

- проверка без модели: все идентификаторы существуют;
- супервизия вторым вызовом: «какие утверждения не подтверждаются своими основаниями» — тоже выбор из списка;
- устаревание: отпечаток оснований изменился → устарело именно это утверждение, перегенерируется оно одно;
- в документе основания — ссылки. Текст с основаниями и есть «мясо, которое можно провалидировать».

Место ИИ — не сборка. Сборка должна быть воспроизводимой и не требовать ключей. Обогащение — отдельная
команда; её результат коммитится и проходит ревью; сборка только подставляет сохранённое и помечает
устаревшее.

Промты: файлы по умолчанию внутри расширения; файл с тем же именем в папке продукта его заменяет.

Граница: несколько вызовов с супервизией — это уже workflow, а движок workflow — предмет SayBatyr. В
библиотеке документации его повторять нельзя. Расширение ИИ остаётся маленьким: «срез модели → утверждения с
основаниями → проверка».

### 3.4 Reqnroll

Детерминированная часть: тег сценария с идентификатором операции → сценарий становится требованием, ссылка
ведёт на `.feature`. ИИ-помощник уместен в одном месте: предложить, к каким операциям относится сценарий без
тега — выбор из предъявленного списка операций; человек принимает и коммитит.

### 3.5 Ручные документы

Два направления, оба через идентификаторы, оба после модели:

- ручной документ вставляет собранный фрагмент: область между метками, которую сборка обновляет;
- ручной документ объявляет, о чём он («об операции такой-то»), и документ области ссылается на него.

Целостность: ссылка на идентификатор, которого больше нет, — сообщение при сборке.

### 3.6 Диаграммы

Библиотека может быть **производителем** формата из спецификации SayBatyr: `classDiagram` с директивами
`diagram`, `assembly`, `type`, `member`, `edge` — всё это в модели есть. Просмотр с diff и раскрытием — дело
SayBatyr, не библиотеки. Риск: профиль требует Mermaid 11.15 (подписанные `namespace`); показывает ли это
GitHub — надо проверить до работы.

### 3.7 Что сейчас не так

1. **Рабочий код в пакете документации.** `ConnectDomains` — рантайм с DI, а первая версия — «только
   документация». Атрибут `[On]` остаётся в базовом пакете, подключение уходит в расширение.
2. **Счётчик покрытия противоречит образцу.** Образец говорит: тест на каждый метод не нужен и вреден. А
   документ пишет «3 of 5 operations have requirements» и «No requirements» под каждой операцией — это
   толкает писать тест на каждый метод. Убрать.
3. **Ничего не проверено на настоящем продукте.** Девять PR за день на игрушечном примере, код владелец не
   читал. Атрибуты по роли позволяют пометить существующие классы без переделки продукта — проба дешёвая и
   скажет больше, чем любая новая возможность.
4. **Три продукта в одном.** (А) генератор документации бизнес-API — ясная польза, почти готов. (Б) правила —
   расширение. (В) документация со знаниями и ИИ — большая тема на границе с SayBatyr и KnowBatyr. Если (В)
   начать до модели и пробы, она поглотит (А).

### 3.8 Предлагаемый порядок

1. Модель бизнес-API и идентификаторы; вывод Markdown поверх неё; подключение связей — в расширение; убрать
   счётчик покрытия.
2. Проба на настоящем продукте (решение владельца).
3. Диаграмма Mermaid из модели.
4. Точки расширения: добавить узлы (Reqnroll, ручные документы), добавить вывод.
5. Расширение ИИ: `IChatClient`, промты-файлы, утверждения с основаниями, отдельная команда.
